# Skill 3.5: forensic-auditor-skill

**Purpose**: Execute complete forensic analysis of repository (23-section protocol).

**Input**: repo_dna.json + readme_audit.json + repo code/files  
**Output**: forensic_report.json (complete system analysis)  
**Speed**: 5-10 seconds per repo  
**Scope**: FULL system discovery, verification, capability inventory, asset extraction, business value

## Analysis Protocol (23-Section Deep Dive)

### Section 1: System Identity
**Task**: Determine what this system actually is.

**Questions**:
- Does the README match the code?
- What is the primary workflow?
- Who uses it? How?
- What are the real entry points?
- What is the data model?

**Action**: Read main entry points, README, package.json, Dockerfile. Do NOT assume docs are correct.

---

### Section 2: Architecture Reconstruction
**Task**: Map the actual architecture.

**Questions**:
- What is the user-facing interface?
- What services/modules exist?
- How do they communicate?
- What is the data flow?
- Are there any hidden subsystems?

**Action**: Trace imports, analyze file structure, identify layers/modules.

---

### Section 3: Capability Inventory
**Task**: List EVERY meaningful capability (documented or hidden).

**Rules**:
- Look inside utilities, scripts, CI/CD, configs
- Separate core from supporting
- Score each 0-5 for maturity
- Never skip experimental features

---

### Section 4: Asset Extraction
**Task**: Identify all valuable, reusable intellectual property.

**Examples**:
- Algorithms, parsers, generators
- Design patterns, templates
- Deployment configs
- Prompts, agent definitions
- Business logic, calculators
- Integration patterns

---

### Section 5: System Lineage
**Task**: Reconstruct development history (where evidence exists).

**Questions**:
- What was built first?
- What changed significantly?
- What was abandoned?
- What experiments survived?
- What is the current direction?

**Rule**: Distinguish VERIFIED, INFERRED, UNKNOWN.

---

### Section 6: Dependency Graph
**Task**: Map all dependencies (internal + external).

**Questions**:
- If component X disappears, what breaks?
- Are there circular dependencies?
- What are the critical paths?
- What dependencies are outdated/vulnerable?

---

### Section 7: Data Flow
**Task**: Trace important data through system.

**For each major workflow**:
```
INPUT → VALIDATION → PROCESSING → TRANSFORMATION → STORAGE → RETRIEVAL → OUTPUT
```

---

### Section 8: AI/Agent Analysis
**Task**: If AI components exist, perform dedicated analysis.

**For each agent**:
- Name, purpose, inputs, tools, memory, outputs
- Authority (what can it do?)
- Failure modes
- Reusability
- Maturity

---

### Section 9: Security Audit
**Task**: Analyze actual attack surface (not theoretical).

**Focus**:
- Auth/AuthZ mechanisms
- Secrets management
- Exposed endpoints
- Injection risks
- Dependency vulnerabilities
- Privilege escalation paths

---

### Section 10: Production Readiness
**Task**: Score across 9 dimensions (0-100 each).

**Scoring**:
- 0–20: Prototype
- 21–40: Experimental
- 41–60: Functional
- 61–80: Pre-production
- 81–95: Production-ready
- 96–100: Mature production system

---

### Sections 11-23
Similar deep-dive protocols for:
- Technical debt
- Duplication/consolidation
- Reusability
- Productization
- Business value
- System maturity
- Single source of truth
- What actually exists
- What's missing (prioritized)
- Critical path (10 steps to production)
- Architectural recommendation
- Final system map
- Executive verdict

## Copy-Paste Prompt Template

````
You are a forensic system analyst. Your task is to perform a complete 23-section analysis of a GitHub repository.

**CRITICAL RULES:**
1. Inspect before concluding — verify claims against code
2. Never invent capabilities
3. Distinguish VERIFIED / INFERRED / UNKNOWN
4. Focus on actual implementation, not documentation
5. Return valid JSON conforming to schema

**Input:**
```json
{
  "owner": "{{OWNER}}",
  "repo": "{{REPO}}",
  "repo_dna": {{DNA_JSON}},
  "readme_audit": {{AUDIT_JSON}},
  "file_contents": {
    "README.md": "{{README or null}}",
    "package.json": "{{JSON or null}}",
    "Dockerfile": "{{TEXT or null}}",
    "src/index.ts (or main entry)": "{{CODE or null}}",
    ".github/workflows/...": "{{WORKFLOW YAML or null}}"
  }
}
```

**Steps (execute in order):**

1. **System Identity**: Read README, package.json, Dockerfile, main entry point
   - What is the purpose? (from code, not docs)
   - What are the major capabilities? (from implementation)
   - Write a 1-paragraph system definition

2. **Architecture Reconstruction**: Map subsystems
   - Identify entry points
   - Trace dependencies between modules
   - Classify as: platform/applications/services/agents/data/infrastructure/automation/knowledge/security/operations

3. **Capability Inventory**: List every meaningful capability
   - Scan source code for hidden features
   - Check CI/CD for automation capabilities
   - Score each 0-5 for maturity

4. **Asset Extraction**: Identify reusable IP
   - Code modules, algorithms, patterns
   - Deployment configs, templates
   - Prompts, schemas, integrations

5. **System Lineage**: Reconstruct development history
   - Look for version changes, branch structure
   - Identify major refactors
   - Mark as VERIFIED/INFERRED/UNKNOWN

6. **Dependency Graph**: Map all dependencies
   - Internal: component-to-component
   - External: packages and versions
   - Identify critical paths

7. **Data Flow**: Trace data workflows
   - For each major workflow: input → output
   - Identify storage, caching, retrieval

8. **AI/Agent Analysis** (if applicable):
   - Identify agents, tools, memory systems
   - Evaluate maturity and reusability

9. **Security Audit**: Analyze attack surface
   - Auth/AuthZ mechanisms
   - Secrets handling
   - Exposed endpoints
   - Vulnerable dependencies

10. **Production Readiness**: Score 9 dimensions
    - Functionality, error handling, testing, security, scalability, reliability, deployment, monitoring, docs

11. **Technical Debt**: Identify duplications, dead code, TODOs
    - Separate: MUST FIX, SHOULD FIX, OPTIONAL

12. **Duplication/Consolidation**: Find redundant implementations
    - Recommend consolidation strategy

13. **Reusability Analysis**: Rate each component
    - SYSTEM_ONLY → COMMERCIAL_PRODUCT

14. **Productization Analysis**: Identify product opportunities
    - Only if credible foundation exists

15. **Business Value**: Rank highest-value assets
    - Top 6 valuable capabilities/assets

16. **System Maturity**: Score 14 categories
    - Calculate overall maturity (0-100)

17. **Single Source of Truth**: Map canonical locations
    - Identify conflicts, duplications

18. **What Actually Exists**: Three lists
    - Verified existing, Partially implemented, Claimed but not verified

19. **What's Missing**: Prioritize gaps
    - P0 blocking, P1 critical, P2 important, P3 optimization

20. **Critical Path**: 10-step sequence to production
    - Each step depends logically on previous

21. **Architectural Recommendation**: Advise on KEEP/MODIFY/CONSOLIDATE/EXTRACT/DEPRECATE/REBUILD

22. **Final System Map**: Create ASCII hierarchy of all components

23. **Executive Verdict**: 9-part summary
    - What it is, what it can do, what it can't, valuable assets, risks, opportunities, what to keep, what to consolidate, what's next, commercial potential, final score

**Output:** Valid JSON matching forensic_report.schema.json

**Validation:**
- [ ] All object keys match schema exactly
- [ ] All required fields present
- [ ] No invented capabilities (only evidence-based)
- [ ] JSON is valid
- [ ] Timestamps are ISO 8601

**Return:** JSON output only, no markdown.
````
